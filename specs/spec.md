# Spec: ฟีเจอร์แจ้งเตือนสต็อกต่ำ และรายงานมูลค่าสต็อก

## 1. เป้าหมาย (Goal)
เพิ่มความสามารถให้ระบบ inventory แจ้งเตือนผู้จัดการเมื่อสินค้าใดต่ำกว่า
threshold และให้ผู้จัดการดูรายงานมูลค่าสต็อกแยกตามหมวดหมู่ได้

## 2. User Story
| รหัส | User Story |
|---|---|
| US-01 | As a พนักงานคลังสินค้า, I want บันทึกการรับ/จ่ายสินค้าพร้อมอัปเดตสต็อกทันที, so that สต็อกในระบบสะท้อนจำนวนจริง |
| US-02 | As a ผู้จัดการ, I want รับการแจ้งเตือนทันทีเมื่อสินค้าใดต่ำกว่า threshold, so that สั่งซื้อได้ก่อนของหมด |
| US-03 | As a ผู้จัดการ, I want ดูมูลค่ารวมของสต็อกแยกตามหมวดหมู่, so that ตัดสินใจด้านการเงินได้ |
| US-04 | As a ผู้จัดการ, I want ตั้งค่า threshold แยกรายสินค้าได้ (ถ้าไม่ตั้งค่าให้ใช้ค่า default = 10), so that สินค้าแต่ละชนิดมีจุดแจ้งเตือนที่เหมาะสม |
| US-05 | As a ผู้จัดการ, I want ให้ระบบส่งแจ้งเตือนไปทุกช่องทางที่เปิดใช้งานไว้ (email และ/หรือ sms พร้อมกัน), so that ไม่พลาดข่าวสารไม่ว่าจะเช็คช่องทางไหนก่อน |

## 3. Acceptance Criteria (Given-When-Then)

### AC ของ US-01
```gherkin
Scenario: บันทึกรับสินค้าเข้าสต็อก
  Given สินค้า "น็อตหกเหลี่ยม M6" มีสต็อก 100 ตัว
  When พนักงานบันทึกรับเข้า 50 ตัว
  Then สต็อกคงเหลือ 150 ตัว

Scenario: บันทึกจ่ายสินค้าแต่สต็อกไม่พอ (ปฏิเสธรายการ)
  Given สินค้า "น็อตหกเหลี่ยม M6" มีสต็อก 10 ตัว
  When พนักงานพยายามบันทึกจ่ายออก 20 ตัว
  Then ระบบปฏิเสธการทำรายการและคืนค่า error "สต็อกไม่เพียงพอ"
  And สต็อกยังคงเป็น 10 ตัว (ไม่เปลี่ยนแปลง)
  And ระบบไม่ส่งการแจ้งเตือนใด ๆ เพราะรายการไม่สำเร็จ
```

### AC ของ US-02
```gherkin
Scenario: จ่ายสินค้าจนสต็อกต่ำกว่า threshold
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 20 เมตร และ threshold = 15
  When พนักงานบันทึกจ่ายออก 8 เมตร
  Then สต็อกคงเหลือ 12 เมตร
  And ระบบส่งข้อความแจ้งเตือนที่มีชื่อสินค้า จำนวนคงเหลือ และ threshold
       เช่น "[Email] สินค้า สายไฟ 2.5 sq.mm เหลือ 12 เมตร (ต่ำกว่า threshold 15)"
       ไปยังทุกช่องทางที่เปิดใช้งานสำหรับสินค้านั้น

Scenario: จ่ายสินค้าโดยสต็อกยังสูงกว่า threshold
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 50 เมตร และ threshold = 15
  When พนักงานบันทึกจ่ายออก 10 เมตร
  Then สต็อกคงเหลือ 40 เมตร
  And ระบบไม่ส่งการแจ้งเตือน

Scenario: สต็อกหลังจ่ายเท่ากับ threshold พอดี (boundary case)
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 20 เมตร และ threshold = 15
  When พนักงานบันทึกจ่ายออก 5 เมตร
  Then สต็อกคงเหลือ 15 เมตร
  And ระบบไม่ส่งการแจ้งเตือน (เงื่อนไขคือ "น้อยกว่า" threshold เท่านั้น ใช้ operator "<"
       ไม่ใช่ "<=" — เท่ากับ threshold ถือว่ายังไม่ต่ำกว่า)

Scenario: จ่ายสินค้าซ้ำขณะสต็อกต่ำกว่า threshold อยู่แล้ว
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 12 เมตร (ต่ำกว่า threshold 15 อยู่แล้ว)
  When พนักงานบันทึกจ่ายออกอีก 2 เมตร (สต็อกเหลือ 10 เมตร)
  Then ระบบส่งการแจ้งเตือนซ้ำอีกครั้ง (แจ้งเตือนทุกครั้งที่มีการจ่ายขณะสต็อกยังต่ำกว่า threshold
       ไม่ใช่แจ้งครั้งเดียวแล้วเงียบ เพื่อให้ผู้จัดการเห็นสถานการณ์ล่าสุดเสมอ)

Scenario: รับสินค้าเข้าจนสต็อกกลับสูงกว่า threshold
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 10 เมตร (ต่ำกว่า threshold 15 อยู่)
  When พนักงานบันทึกรับเข้า 20 เมตร (สต็อกเป็น 30 เมตร)
  Then ระบบไม่ส่งการแจ้งเตือนสต็อกต่ำ (เพราะการรับเข้าไม่มีทางทำให้สต็อกต่ำกว่า threshold ได้
       ระบบตรวจแจ้งเตือนเฉพาะตอนจ่ายออกเท่านั้น ไม่ครอบคลุมการแจ้ง "กลับสู่ปกติ" ในรอบนี้)
```

### AC ของ US-03
```gherkin
Scenario: ดูรายงานมูลค่าสต็อกแยกตามหมวดหมู่
  Given มีสินค้าในหมวด "สายไฟ" มูลค่ารวม 5,000 บาท
  And มีสินค้าในหมวด "น็อตและสกรู" มูลค่ารวม 1,200 บาท
  When ผู้จัดการเรียกดูรายงานมูลค่าสต็อก
  Then ระบบแสดงมูลค่ารวมแยกตามหมวดหมู่ถูกต้องทุกหมวด
  And ระบบแสดงมูลค่ารวมทั้งหมดของทุกหมวดรวมกัน (6,200 บาท)

Scenario: ดูรายงานเมื่อไม่มีสินค้าในสต็อกเลย
  Given ไม่มีสินค้าในระบบ
  When ผู้จัดการเรียกดูรายงานมูลค่าสต็อก
  Then ระบบแสดงมูลค่ารวมเป็น 0 บาท โดยไม่เกิด error

Scenario: มีสินค้าที่ไม่ได้ระบุหมวดหมู่ (uncategorized)
  Given มีสินค้า "อุปกรณ์เบ็ดเตล็ด" ที่ไม่ได้กำหนดหมวดหมู่ มูลค่า 300 บาท
  When ผู้จัดการเรียกดูรายงานมูลค่าสต็อก
  Then ระบบจัดสินค้านี้ไว้ในหมวด "ไม่ระบุหมวดหมู่" (Uncategorized)
       และรวมมูลค่าเข้ากับยอดรวมทั้งหมดด้วย
```

## 4. In Scope / Out of Scope
**In Scope:** บันทึกรับ/จ่าย + อัปเดตสต็อกใน memory (ไม่ใช้ฐานข้อมูลถาวร ข้อมูลหายเมื่อโปรแกรมปิด),
แจ้งเตือน email/sms (print แทนส่งจริง), รายงานมูลค่าแยกหมวด, ตั้งค่า threshold รายสินค้า (default = 10 ถ้าไม่ระบุ)

**Out of Scope:** ส่ง email/sms จริง, ระบบ login/สิทธิ์ผู้ใช้งาน, ฐานข้อมูลถาวร,
การแจ้งเตือน "สต็อกกลับสู่ปกติ" เมื่อรับสินค้าเข้าจนพ้น threshold, การแจ้งเตือนผ่าน Line/Push Notification

## 5. Functional Requirements (FR)
| รหัส | ความต้องการ | จาก Story |
|---|---|---|
| FR-01 | ระบบต้องอัปเดตสต็อกทันทีหลังบันทึกรับ/จ่าย | US-01 |
| FR-02 | ระบบต้องตรวจสต็อกก่อนจ่าย และปฏิเสธ (ไม่อัปเดตสต็อก ไม่ส่งแจ้งเตือน) ถ้าจำนวนที่จ่ายมากกว่าสต็อกคงเหลือ | US-01 |
| FR-03 | ระบบต้องแจ้งเตือนทุกครั้งที่จ่ายสินค้าสำเร็จแล้วสต็อกคงเหลือ "น้อยกว่า" (`<`) threshold ของสินค้านั้น (ไม่ใช่ `<=`) | US-02 |
| FR-04 | ระบบต้องคำนวณมูลค่าสต็อก (จำนวน × ราคาต่อหน่วย) แยกตามหมวดหมู่ได้ รวมถึงกลุ่ม "ไม่ระบุหมวดหมู่" | US-03 |
| FR-05 | ระบบต้องอนุญาตให้ตั้งค่า threshold แยกตามสินค้าแต่ละรายการ ถ้าไม่ระบุให้ใช้ค่า default = 10 | US-04 |
| FR-06 | ระบบต้องส่งข้อความแจ้งเตือนไปยังทุกช่องทาง (email/sms) ที่เปิดใช้งานไว้สำหรับสินค้านั้นพร้อมกัน โดยข้อความต้องระบุ ชื่อสินค้า จำนวนคงเหลือ และค่า threshold | US-05 |

## 6. Non-Functional Requirements (NFR)
| รหัส | มิติ | ความต้องการ (ต้องวัดได้) |
|---|---|---|
| NFR-01 | Performance | รายงานมูลค่าสต็อกสำหรับ 1,000 รายการสินค้า ต้องคำนวณเสร็จภายใน 1 วินาที เมื่อรันบนเครื่องพัฒนา (local, single-thread, ไม่มี I/O ภายนอก) |
| NFR-02 | Maintainability / Extensibility | Business logic ของสต็อก (การรับ/จ่าย/คำนวณ) ต้องไม่ผูกติดกับการแจ้งเตือนโดยตรง เพื่อให้เพิ่มช่องทางแจ้งเตือนใหม่ (เช่น Line, Push) ได้โดยไม่แก้โค้ดส่วน business logic เดิม (ดูรายละเอียดการออกแบบใน Design Notes) |
| NFR-03 | Reliability | ถ้าช่องทางแจ้งเตือนหนึ่งล้มเหลว (เช่น จำลองว่า SMS ส่งไม่สำเร็จ) ระบบต้องยังคงบันทึกรายการสต็อกสำเร็จ และพยายามส่งแจ้งเตือนผ่านช่องทางอื่นที่เหลือต่อไปตามปกติ ไม่ล้มทั้งระบบ |

## 7. Design Notes
- การแจ้งเตือนต้องแยกออกจาก business logic ของสต็อกอย่างเด็ดขาด (ดู NFR-02)
- คาดว่าจะมีหลายช่องทางแจ้งเตือนในอนาคต ควรออกแบบให้เพิ่มช่องทางใหม่ได้ง่ายโดยไม่แก้โค้ดเดิม
  (แนวทาง: ใช้ interface/protocol กลางสำหรับ notifier แล้วให้แต่ละช่องทาง implement แยกกัน)
